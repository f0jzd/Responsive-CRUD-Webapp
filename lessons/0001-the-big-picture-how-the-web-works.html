The Big Picture: How the 3 Pieces Connect

Before looking at code, let's understand the physical reality of how a modern web app like our Book Catalog actually functions.

Why Are There Three Separate Pieces?

When you open a web application, you are not interacting with one giant monolith. Instead, three distinct players work together across space and time:

  1. The Frontend (Browser Client): Built with Angular. It runs locally on your laptop inside Chrome or Safari. Its only job is to turn data into pixels, listen to your mouse clicks, and update the screen instantly.
  2. The Backend (Web API Server): Built with C# & ASP.NET Core. It runs in the background. Its job is to guard access, enforce business logic, and answer questions sent over the network.
  3. The Database (Storage Engine): Powered by SQLite & EF Core. It lives on a hard drive (a file named books.db). Its job is to remember books even if the computer restarts.
The Golden Rule of the Web
A web browser cannot directly read files from your database file on disk. If browsers could read server hard drives directly, anyone visiting a website could steal private user passwords! The backend acts as a strict security guard standing between the browser and the database.

Step 1: The User Opens the Catalog

The user navigates to the website in their browser. The Angular application boots up into memory. At this instant, the catalog list is empty because the browser does not yet have any book data.

Why Real-Time Search Happens in the Browser

In Issue #1, the requirement says: "Real-time client-side search input filters books by title/author."

Notice the words client-side. Once the browser receives the full list of books from the server, all the book information sits safely in your computer's RAM. When you type letters into the search box, Angular filters the list already in memory. It does not need to wait for the server on every keystroke, making the catalog feel instant and snappy!
